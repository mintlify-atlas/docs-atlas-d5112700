OASIS Seguros is a full-stack insurance management platform built as a Next.js 16 monolith with React 19. Rather than splitting the application into separate microservices, the project consolidates the web server, API routes, and Server Actions into a single deployable unit while keeping business logic cleanly separated through Clean Architecture. This page gives you a bird's-eye view of every runtime component, how they communicate, and why each technology was chosen.

## Component Overview

| Component | Technology | Role |
|---|---|---|
| **Web application** | Next.js 16 + React 19 | Renders UI, handles routing via App Router, exposes API routes and Server Actions |
| **Authentication** | Better-Auth | Session management, RBAC, OAuth accounts, refresh tokens |
| **Database** | PostgreSQL 15 via Prisma ORM | Persistent storage across 8 logical schemas with full referential integrity |
| **Cache & sessions** | Redis | Stores Better-Auth sessions and application-level cache to reduce DB round-trips |
| **Background workers** | pg-boss | Scheduled jobs for payment reminders, overdue detection, and notification dispatch — runs as a separate process sharing the same PostgreSQL connection |
| **UI components** | Shadcn UI + Tailwind CSS 4 | Accessible, composable component library styled with utility-first CSS |
| **Validation** | Zod | Schema validation on DTOs, Server Action inputs, and environment variables |
| **External comms** | Twilio (SMS) + SMTP (email) | Outbound notifications; both services degrade gracefully when credentials are absent |

## Key Design Decisions

### Why Clean Architecture?

OASIS Seguros separates code into three concentric layers — **Domain**, **Application**, and **Infrastructure** — so that business rules are never coupled to frameworks or databases. This means you can swap Prisma for a different ORM, replace Next.js Server Actions with a REST controller, or stub out repositories in tests without touching a single line of business logic. See [Clean Architecture](/architecture/clean-architecture) for the full breakdown.

### Why Multi-Schema PostgreSQL?

Instead of prefixing every table name (`auth_user`, `clients_client`, …) or deploying separate databases per domain, OASIS Seguros uses PostgreSQL schemas to create logical namespaces (`auth`, `clients`, `insurance`, `payments`, `claims`, `notifications`, `audit`, `blockchain`). Each schema groups related models, enforces clear ownership boundaries, and allows fine-grained permission grants — all within a single PostgreSQL instance and a single Prisma data source. See [Database Schema](/architecture/database-schema) for the complete schema layout.

### Why pg-boss?

pg-boss stores its job queue inside the same PostgreSQL database, removing the need for a dedicated message broker. Jobs survive application restarts, retries are configurable, and every execution is logged to the `notifications.job_execution` table for full observability. The worker process shares Prisma models with the web app and is built from the same Docker image.

<Note>
  All four services — `web`, `worker`, `db`, and `redis` — are wired together in `docker-compose.yml`. Running `docker-compose up -d` is the recommended way to start a full local environment.
</Note>

## Environment Variables

At minimum, three variables must be set before the application starts:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string (`postgresql://user:pass@host:5432/db`) |
| `REDIS_URL` | Redis connection string (`redis://localhost:6379`) |
| `BETTER_AUTH_SECRET` | Session signing secret — minimum 32 characters |

Optional variables (`TWILIO_*`, `SMTP_*`) enable SMS and email dispatch. Both services handle missing credentials gracefully and log a warning instead of crashing.
